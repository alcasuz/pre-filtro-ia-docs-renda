# Decision log

| Date | Decision | Rationale | Alternatives discarded |
|---|---|---|---|
| 2026-10-24 | Repository named pre-filtro-ia-docs-renda (instead of analisador-renda-ia) | "Pre-screening" (pré-filtro) signals that the AI triages and the final decision has human review | analisador-renda-ia (suggests the AI decides alone) |
| 2026-10-24 | Local development (repo cloned on my machine + Claude Code in VS Code) | The API key stays only in the local .env, Gemini calls work without network setup, and I practice real git | Claude Code in the cloud (would require configuring secrets and network access in the remote environment) |
| 2026-10-24 | Environment: Intel Mac without Homebrew; tools installed with official installers | Homebrew no longer supports Intel Macs | Homebrew |
| 2026-10-24 | v1 scope: pay stubs only; bank statements, INSS benefits, income tax returns and owner's draw kept in the v2 backlog | Pay stubs have a more predictable structure and allow measuring accuracy with the available test set; bank statements have the open problem of identifying income from individuals who sell as such | Including bank statements in v1; 5 document types (few examples per type; owner's draw would require a corporate document) |
| 2026-10-24 | Premise: the LLM only extracts; every calculation and decision belongs to the code | LLMs make arithmetic mistakes and the credit decision must be auditable | LLM computing income and deciding |
| 2026-10-24 | The LLM returns every pay stub line classified (description, amount, counts/doesn't count), never totals; CPF normalization and validation and name similarity live in code | Errors are traceable per line, the eval measures accuracy per line and the math is deterministic | LLM returning the total accepted earnings and the similarity score |
| 2026-10-24 | Name similarity computed by a formula in code, not by the LLM | Deterministic, calibratable through the eval, auditable and token-free; the LLM produces a plausible number, it doesn't calculate | LLM estimating similarity |
| 2026-10-24 | The extraction JSON carries only the fields the rules use; the generated pay stub shows all real fields | Fewer tokens, less latency and fewer error points, without losing realism | Extracting the full pay stub |
| 2026-10-24 | Valid income = 3-month average of gross fixed pay ≥ 3× the installment (replaces the initial decision to use net pay) | Fewer fields to extract and no math with deductions = fewer LLM error points; removing overtime from net pay would require prorating deductions | Net pay − variable pay; proportional net pay; total earnings; lowest month; latest month |
| 2026-10-24 | 3 pay stubs for consecutive pay periods, formatted YYYY-MM; multiplier kept at 3× gross pay | YYYY-MM sorts chronologically as text; consecutive months prevent cherry-picking good months | MM/YYYY; non-consecutive months |
| 2026-10-24 | Time windows counted from a fixed analysis_date in the applicant record | Deterministic eval: same input, same output | Counting from the run date |
| 2026-10-24 | Vacation pay counts as income; the 1/3 vacation bonus doesn't. A separate vacation pay stub is added to the regular one; a separate 13th-salary pay stub is ignored | Replaces the salary for the vacation days and avoids a false negative in the vacation month; the 1/3 and the 13th salary are annual extras | Excluding all vacation pay (would drag down the average of anyone who took vacation); adding every pay stub in the pay period |
| 2026-10-24 | CPF takes priority: if it matches the record, the name is not evaluated; without a CPF, the name similarity rule applies | The CPF is a unique identifier; avoids sending applicants with abbreviated or changed names to review | Requiring both name and CPF to match |
| 2026-10-24 | Name: ≥95% similarity ok; 50% to <95% human review; <50% reject | Automatic rejection only with high certainty, because false negatives are not reviewed; initial thresholds to be calibrated in the eval | Single cutoff at 90% (would reject legitimate applicants with abbreviated names) |
| 2026-10-24 | Human review only for approvals and suspected fraud; rejection is automatic, with the reason shown to the applicant | Focuses analysts where the credit risk is; the false negative becomes the critical metric | Reviewing every case (no cost gain) |
| 2026-10-24 | Document typing with 4 outputs (payslip, payslip_vacation, payslip_13th, other); every "other" is rejected with the message "we currently accept pay stubs only" | A single message works for bank statements, INSS benefits or files that aren't documents, and always tells the applicant what to send; the test set keeps the detailed true type for analysis | Separate categories for "other proof of income" vs "not a proof of income"; specific rules to identify bank statements |
| 2026-10-24 | OCR: Tesseract | Open source, lightweight, returns per-word confidence and runs on a Mac and on the demo's Linux server | PaddleOCR (heavier to install), Apple Vision (Mac only), EasyOCR (heavier; kept as a fallback) |
| 2026-10-24 | Legibility decided by the average OCR confidence against a threshold in code | Numeric, stable signal, independent of the model's self-assessment | Legibility flag set by the LLM |
| 2026-10-24 | Two-level eval: fields per document and final decision per applicant | Separates extraction errors (the LLM misread) from rule errors (the code decided wrong) | Measuring only the final decision |
| 2026-10-24 | Test set of 32 applicants, ~50% approve and ~50% reject/review, with edge cases around 3× and no tolerance in the rule | Every path of every rule is tested; the enriched set prevents "approve everyone" from looking good; edge cases measure extraction fragility | 75% approve, mirroring production (the reject paths wouldn't fit); 5% income tolerance (would hide extraction errors) |
| 2026-10-24 | Extraction checked automatically against the test set CSVs; images checked by visual inspection of a sample, including every deliberately degraded document | The CSVs are the source of truth and code comparison is exact; the sample ensures each image tests what its scenario claims | Checking every extraction by hand |
| 2026-10-24 | Decision ground truth filled in by hand and frozen before any AI run; later corrections only with a logged reason | Avoids anchoring bias and inflated accuracy; applying the rules by hand reveals ambiguities the AI would resolve silently | Building the ground truth by reviewing the AI's outputs |
| 2026-10-24 | Ground truth with controlled vocabulary: decision as approve/reject/review and reason as a fixed code; applicant messages derived from the code | The eval compares exact text; free-text reasons aren't comparable, and codes make it possible to measure whether the applicant got the right reason | Free-text decision and reason |
| 2026-10-24 | Test set (data and generator script) versioned in the repository | The set is 100% fictional and is needed to reproduce the published results | Keeping the data out of git |
| 2026-10-24 | Single core shared by the front end and the eval; only the multiplier is configurable in the front end (no rule toggles) | The eval numbers measure the same system as the demo; rule toggles would add complexity without learning value and invalidate the ground truth | Separate code for front end and eval; rule toggles in the front end |
| 2026-10-24 | Extraction cache per document and prompt version | Changing a rule uses no API quota; the front end recalculates the decision instantly | Calling the LLM on every run |
| 2026-10-24 | Public demo with the fictional test set and cached extractions only, no uploads | Avoids receiving real documents from visitors (the free tier may use submitted data) and protects my key's quota | Open uploads in the public demo |
| 2026-10-24 | Repository in English (docs, file names, CSV columns and codes), except README.pt-BR.md; document content (names, line-item descriptions) stays in Portuguese | Makes the project readable for anyone, anywhere; the pay stubs are Brazilian and the model must be tested on Portuguese documents | Everything in Portuguese; translating the pay stub content as well (would change the problem being tested) |
| 2026-10-24 | Main README in English (README.md) with a Portuguese version (README.pt-BR.md) | Reaches recruiters on international teams without losing the Brazilian audience | Portuguese only |
| 2026-10-24 | Time window: the 4 months prior to the month of analysis_date, not including that month (e.g., an analysis in 2026-10 accepts pay periods 2026-06 to 2026-09) | The current month's pay stub doesn't exist yet on the analysis date; including it would in practice remove the 1-month tolerance | Window including the analysis month |
2026-10-24 | Precedence: reject always takes precedence over suspected fraud | Human review exists only for cases that could be approved; reviewing a case that would be rejected anyway costs analyst time without changing the outcome | Fraud flag always sends the case to review
2026-10-24 | The fraud flag is always recorded with the decision, even when the case is rejected | Measures how many fraud attempts never reach human review, at zero cost | Discarding the flag on rejected cases; generic rejection message when fraud is flagged (would leave honest applicants flagged by mistake without guidance)
2026-10-24 | Test images generated locally with Pillow from the CSVs; Gemini rate limits discovered empirically, in batches, with every extraction cached and a graceful stop on HTTP 429 | Image generation costs nothing and is reproducible; the free tier doesn't bill when the limit is exceeded, and caching means no call is lost | Generating images with an AI image model; reading the limits from documentation only
